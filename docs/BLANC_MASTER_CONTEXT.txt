--- I.1  MODELO DE TRABAJO: ARQUITECTO + EJECUTOR --------------------------------

Este documento esta escrito para un modelo de dos roles:

  IA ARQUITECTA (quien lee esto)
    Decide QUE se construye, en que orden, con que alcance y bajo que criterio.
    Descompone el trabajo en ordenes ejecutables. Valida resultados. Mantiene
    la coherencia del proyecto en el tiempo. NO escribe codigo.

  EJECUTOR (Claude Code u otro agente con acceso al repositorio)
    Audita, implementa, prueba y documenta UNA orden a la vez. Reporta con
    fidelidad. No amplia alcance. No toma decisiones de arquitectura ni de
    negocio por su cuenta.

  DUENA / CLIENTE
    Unica autoridad sobre decisiones de negocio y producto. Hay 11 preguntas
    abiertas que le pertenecen (Parte IV.3). Ni la arquitecta ni el ejecutor
    pueden resolverlas.

El protocolo concreto para emitir ordenes esta en la Parte VII.

--- III.2  AUTENTICACION --------------------------------------------------------

QUIEN EMITE EL JWT: Supabase Auth, siempre. Blanc NUNCA emite tokens [DECISION].

VALIDACION [IMPLEMENTED - shared/auth/jwt-auth.guard.ts]:
  1. @Public() -> pasa sin token
  2. Extrae "Bearer <token>" -> si falta: 401 TOKEN_AUSENTE
  3. jwt.decode(complete:true) para leer SOLO el header
  4. Selecciona rama por header.alg (NUNCA por el payload):
       HS256 -> jsonwebtoken.verify(token, secretoLegacy,
                {algorithms:['HS256'], issuer})
       ES256 -> jose.jwtVerify(token, resolverClaveJwks,
                {algorithms:['ES256'], issuer})
       otro  -> 401 TOKEN_ALGORITMO_NO_PERMITIDO (sin intentar verificar)
  5. Valida rol contra enum Rol, sub no vacio, forma de sucursales
  6. request.usuario = { sub, rol, sucursales }

  SIN FALLBACK entre ramas. Un token ES256 jamas se verifica contra el secreto
  HS256. Existe test explicito de confusion de algoritmo.

CONSTRUCTOR:
  new JwtAuthGuard(jwtSecretLegacy, reflector, issuerEsperado, resolverClaveJwks)

CODIGOS DE ERROR:
  TOKEN_AUSENTE 401 | TOKEN_INVALIDO 401 | TOKEN_ALGORITMO_NO_PERMITIDO 401
  TOKEN_SIN_ROL_VALIDO 401 | TOKEN_CLAIMS_INVALIDOS 401

  NOTA: los dos ultimos son validaciones de datos de AUTORIZACION emitidas como
  401. Es el acoplamiento que C2 (Parte III.5) propone separar, y es el
  resultado real que produce hoy un JWT legitimo de Supabase.

EXPIRACION: 3600 s [CONFIRMED Dashboard]. ADR-010 dice "minutos": desviacion
  documentada, no corregida.

--- III.3  JWT / ES256 / JWKS  (DEC-026, IMPLEMENTED) ---------------------------

HECHO CENTRAL [CONFIRMED empiricamente]:
  El proyecto Supabase real firma con ES256 (ECC P-256). HS256 solo existe como
  clave "PREVIOUSLY USED" (legacy). Esto invalido la premisa de ADR-024, que
  asumia HS256 vigente.

LIBRERIAS:
  jose ^5.10.0        -> rama ES256/JWKS
  jsonwebtoken ^9.0.2 -> rama HS256 legacy

  AVISO CRITICO: jose@6 es ESM-only e INCOMPATIBLE con el runtime CommonJS de
  este proyecto (falla con "SyntaxError: Unexpected token 'export'"). Se fijo
  jose@^5.10.0, ultima version mayor con build CJS. NO ACTUALIZAR a v6 sin
  migrar el proyecto entero a ESM.

JWKS [IMPLEMENTED - shared/auth/supabase-url.ts + auth.module.ts]:
  resolverSupabaseUrl(env)     -> lee SUPABASE_URL, falla duro fuera de test
  resolverIssuerSupabase(url)  -> `${url}/auth/v1`
  resolverJwksUri(url)         -> `${url}/auth/v1/.well-known/jwks.json`
  createRemoteJWKSet(jwksUri)  -> construido UNA vez en AuthModule

  NO existe SUPABASE_JWKS_URL: la URL se deriva siempre de SUPABASE_URL
  (mitigacion deliberada de SSRF) [DECISION].

CACHE Y ROTACION [delegado a jose, defaults sin override]:
  cooldownDuration 30 s (protege contra refresco abusivo)
  cacheMaxAge 600 s
  Ante kid desconocido, jose refresca automaticamente SOLO si el cooldown ya
  expiro; dentro de la ventana lanza JWKSNoMatchingKey de inmediato
  [CONFIRMED empiricamente: comportamiento correcto y deseado, no un bug].
  Blanc NO implementa logica propia de cache/rotacion [DECISION].

VALIDACIONES: firma, algoritmo restringido, issuer, exp y nbf (automaticos en
  ambas librerias, verificado). NO se valida audience [PENDING].

VARIABLES DE ENTORNO (solo nombres, nunca valores):
  DATABASE_URL, JWT_SECRET, SUPABASE_URL, PORT -> declaradas en .env.example
  SUPABASE_SERVICE_ROLE_KEY                    -> aun NO declarada

--- III.5  AUTORIZACION ---------------------------------------------------------

TRES CONCEPTOS DISTINTOS:
  AUTHENTICATION         "Quien eres"   -> JwtAuthGuard, criptografia
  AUTHORIZATION          "Que puedes"   -> RolesGuard (nivel 1, rol/endpoint)
  BUSINESS AUTHORIZATION "Puedes hacer ESTO sobre ESTE recurso"
                                        -> nivel 2, dentro del use case

PIEZAS [IMPLEMENTED - shared/auth/rol.ts]:
  enum Rol (7, catalogo cerrado por RN-SEG-01):
    SUPER_ADMIN, ADMINISTRADOR, GERENTE, RECEPCIONISTA, MANICURISTA,
    ANALISTA, SOLO_LECTURA
  ClaimsUsuario { sub, rol, sucursales: 'GLOBAL'|string[] }
    sub -> AUTENTICACION | rol y sucursales -> AUTORIZACION
    NO contiene 'activa'. Ningun guard conoce ese concepto hoy [CONFIRMED].
  tieneAlcanceSucursal(claims, sucursalId)
    SUPER_ADMIN -> true | 'GLOBAL' -> true | array -> includes()
    Usado en 5 use cases.
  puedeAsignarRol(actor, actorEsElObjetivo, rolActual, rolNuevo)
    1. Nadie cambia su propio rol
    2. Solo Super Admin asigna Super Admin
    3. Un no-Super-Admin no cambia el rol de un Super Admin
  RolesGuard: consume SOLO request.usuario.rol. Sin @Roles -> return true
    (endpoint abierto a cualquier autenticado). No conoce 'activa', no toca BD.

  Errores 403: ROL_SIN_PERMISO, FUERA_DE_ALCANCE_DE_SUCURSAL,
               ASIGNACION_DE_ROL_NO_PERMITIDA, DESACTIVACION_NO_PERMITIDA

SOURCE OF TRUTH [DECISION - DEC-024]:
  PostgreSQL de Blanc es la fuente de verdad de identidad administrativa, rol,
  activa y sucursales. El JWT es un SNAPSHOT FIRMADO, no fuente de datos.

--- III.6  DEC-001 — CUSTOM ACCESS TOKEN HOOK  [REQUIRES_REDESIGN] --------------

INTENCION ORIGINAL [ADR-024 Decision 1, Proposed]:
  Funcion Postgres `(event jsonb) returns jsonb` registrada como Custom Access
  Token Hook, invocada antes de emitir cada JWT. Consultaria
  identidad_accesos.usuarios y usuarios_sucursales y agregaria los claims 'rol'
  y 'sucursales' antes de que Supabase firmara.

QUE ESTA IMPLEMENTADO DEL HOOK: **NADA**.
  Cero funciones Postgres, cero migraciones, cero configuracion en Supabase,
  cero codigo ejecutable [CONFIRMED por busqueda exhaustiva].
  NO presentarlo como parte de la arquitectura implementada.

POR QUE REQUIRES_REDESIGN:
  Su premisa central (JWT firmado HS256 con el secreto de proyecto, y por tanto
  "no requiere cambios a JwtAuthGuard") se demostro FALSA: la clave vigente es
  ES256/JWKS. El mecanismo sigue siendo viable —es ortogonal al algoritmo— pero
  el diseno necesita ampliarse. Ya no falta acceso externo: falta diseno.

RIESGOS DEL ENFOQUE HOOK:
  - Staleness de claims: hasta 3600 s con permisos revocados
  - Dependencia de mecanismo propietario de Supabase
  - Obliga a que las tablas de Blanc vivan en el Postgres de Supabase
  - Logica de autorizacion partida en dos lenguajes (SQL + TS)
  - No satisface por si solo la constraint de ADR-010
  - REQUIRES_EXTERNAL_ACCESS: nunca se verifico que el hook se ejecute en
    token_refresh en este proyecto. Las pruebas reales de refresh NO lo
    demuestran, porque no hay hook configurado.

ALTERNATIVAS EVALUADAS: A (mantener Hook) | B (Hook + reducir expiry) |
  C (JWT solo autentica, Blanc autoriza contra su PostgreSQL) | D (hibrido).
  Una quinta (verificar contra endpoint remoto por request) se descarto por
  reabrir el rechazo de ADR-010 a la "sesion server-side pura".

RECOMENDACION VIGENTE: alternativa C [RECOMMENDED, no decidido].

--- III.15  TRES CONCEPTOS QUE NO SON EQUIVALENTES ------------------------------

  PROVISIONED      Existe identidad en auth.users Y esta vinculada a Blanc.
                   Marcador: supabase_user_id IS NOT NULL
  AUTHENTICATABLE  La persona tiene credencial valida para autenticarse.
                   Con createUser sin password, puede estar PROVISIONED sin ser
                   AUTHENTICATABLE.
  AUTHORIZED       Blanc reconoce su identidad y le permite operaciones.
                   Requiere rol valido, activa=true y alcance de sucursal.
                   Hoy un usuario puede ser PROVISIONED y AUTHENTICATABLE y aun
                   asi NO estar AUTHORIZED (es exactamente el 401 de III.9).

  Confundir estos tres conceptos es el error de razonamiento mas probable en
  este proyecto.

  EL PATRON DE SILLAS VIRTUALES — por que existe
    La restriccion anti-doble-booking es EXCLUDE USING gist sobre
    manicurista_id. En PostgreSQL NULL = NULL evalua a NULL, no a TRUE, asi que
    una restriccion EXCLUDE NUNCA se dispara entre dos filas con NULL. Dejar
    manicurista_id nulo para las citas sin preferencia habria permitido citas
    simultaneas ILIMITADAS sin que la base protestara: sobreventa silenciosa.
    Solucion: `agenda.sillas` (estacion fisica; el numero de filas por sucursal
    ES la capacidad) y se invierte el modelo — toda cita ocupa exactamente una
    silla, SIEMPRE, y la manicurista es opcional. silla_id es NOT NULL, asi que
    la restriccion siempre tiene un valor real que comparar. Dos restricciones
    para dos escaseces distintas: silla_id (espacio fisico) y manicurista_id con
    WHERE ... IS NOT NULL explicito (persona nombrada). Recepcion reasigna al

PARTE VII — PROTOCOLO DE ORQUESTACION
================================================================================

--- VII.1  CICLO DE TRABAJO ESTABLECIDO -----------------------------------------

Este proyecto ya tiene un patron probado. Respetarlo:

   1. AUDITORIA         El ejecutor inspecciona codigo y documentacion reales y
                        reporta evidencia, contradicciones y decisiones abiertas.
                        NO implementa nada.
   2. ALCANCE MINIMO    La arquitecta confirma un alcance exacto, con listas
                        explicitas de inclusion y exclusion.
   3. IMPLEMENTACION    El ejecutor construye SOLO lo confirmado.
   4. VALIDACION        tests + tsc + build + lint + madge, con salida real.
   5. DOCUMENTACION     Actualizar PROJECT_STATUS.md en la MISMA iteracion.
   6. HANDOFF           Reporte de cierre: que se hizo, que no, que quedo
                        pendiente, cual es el siguiente paso.

Una sola iteracion significativa a la vez. No encadenar fases sin confirmacion.

--- VII.2  FORMATO DE ORDEN DE TRABAJO ------------------------------------------

Una orden bien formada al ejecutor contiene:

  CONTEXTO      Que se acaba de cerrar y por que toca esto ahora.
  OBJETIVO      Una sola cosa, enunciada sin ambiguedad.
  ALCANCE       Lista explicita de lo que SI entra.
  FUERA DE      Lista explicita de lo que NO entra (mas importante que la
  ALCANCE       anterior: previene scope creep).
  RESTRICCIONES Que archivos/areas no tocar. Si hay commit/push autorizado.
  VALIDACION    Que comprobaciones ejecutar y reportar.
  ENTREGABLE    Formato exacto del reporte final.
  PARADA        "Detente al terminar. No continues con X."

  Las ordenes que mejor han funcionado en este proyecto son las que separan
  AUDITAR de IMPLEMENTAR en iteraciones distintas.

--- VII.3  REGLAS PARA LA IA ARQUITECTA -----------------------------------------

  1.  Lee este contexto antes de emitir cualquier orden.
  2.  Exige evidencia del repositorio, no confies en resumenes.
  3.  Distingue hechos de decisiones y decisiones de implementaciones.
  4.  No inventes requisitos de producto. Si no esta documentado, es PENDING.
  5.  Si una cuestion pertenece a la Duena, no la resuelvas: acumulala en IV.3.
  6.  Antes de ordenar mas investigacion, evalua el beneficio marginal. El area
      de autenticacion ya esta exhaustivamente investigada: el retorno de mas
      investigacion ahi es bajo. Ordena formalizar o implementar.
  7.  Cuando el ejecutor reporte una contradiccion, decide explicitamente si se
      corrige, se documenta o se difiere. No la dejes sin resolver.
  8.  Cuando el ejecutor reporte un fallo, exige la salida real, no un resumen.
  9.  No modifiques decisiones cerradas sin justificarlo y registrarlo.
  10. Mantén PROJECT_STATUS.md como fuente maestra: toda decision nueva se
      registra ahi, con historial fechado y sin borrar lo anterior.
